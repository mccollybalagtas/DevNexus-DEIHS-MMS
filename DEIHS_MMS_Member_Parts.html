Member 1 — Foundation: Environment, Database & LAN Deployment

Parts 1, 2, 3, 12 ~6 minutes

Mission: if the database is not reachable, nothing else matters. You make the system build, connect, and run on every PC.

Your 60-second opening

“Our system is a JavaFX desktop application that talks to one shared MySQL database over the school LAN. My part is the foundation. I own the Maven project that builds the app, the database schema that defines every table and relationship, the configuration file that tells each PC where the database lives, and the connection pool that keeps those connections healthy. If my part is correct, every other module just works on any PC in the lab — and if it is wrong, nothing works. So I will show you how it is built, how it connects, and how to prove it is connected.”

What to understand (the logic and the why)

  • One build definition. pom.xml pins Java 21, JavaFX 21.0.13, MySQL Connector/J 9.7.0, HikariCP 5.1.0, jBCrypt 0.4, PDFBox 3.0.3, Gson 2.11.0, and SLF4J. Everyone builds the same thing; no “it works on my machine” version drift.
  • Two entry points, on purpose. javafx:run launches com.deihs.mms.Main for development. The shaded fat jar launches com.deihs.mms.Launcher, a plain main that calls Main.main. Why: when JavaFX is packaged inside a fat jar, starting the Application subclass directly fails with “JavaFX runtime components are missing.” The launcher avoids that.
  • Database first. The schema is the contract between modules: roles, users, maintenance_categories, facilities, equipment, maintenance_requests, request_status_history, maintenance_records, attachments, maintenance_schedules, audit_logs, request_comments, account_requests. Thirteen tables, with foreign keys and status constraints.
  • Configuration is external. db.properties sits on the classpath; AppConfig loads it once and lets -Ddb.host=… override any key. AppConfig.jdbcUrl() assembles host, port, and database name. Why: the developer PC and the school server have different addresses, and you should never recompile to change an IP.
  • Pool, not raw connections. Database builds one HikariCP DataSource with db.pool.size=10. Why: opening a fresh connection on every click is slow and can exhaust MySQL; pooling reuses a small, bounded set and fails fast when the DB is down.
  • LAN reality. Three things must all be true: MySQL listens on the network interface, the database user is allowed to connect from the client IP, and the firewall allows port 3306.

  • Create a dedicated database user for the app (not root) with privileges only on deihs_mms. Accept: the app connects with that user; root is never used.

  2. Show the table list and one relationship: equipment.facility_id → facilities.id, and maintenance_requests.requester_id → users.id.
  3. Open db.properties, show db.host, then start the app with -Ddb.host=… to prove configuration is external.
  4. Log in on the client PC, then run a SELECT on the server showing the new audit row.
  5. Close by showing the fat jar starting without Maven.

Likely questions and short answers

Q: Why MySQL instead of SQLite?

A: Several PCs write at the same time and the data must live in one place. SQLite is a single local file and is a poor fit for concurrent LAN use.

Q: Why HikariCP?

A: It reuses a small pool of connections, bounds resource use, and reports a clear failure when the database is unreachable instead of hanging.

Q: What if the server IP changes?

A: Change db.host in db.properties or pass -Ddb.host=…. Better: give the server a DHCP reservation or static IP.

Q: Are user passwords in the config file?

A: No. The config holds only database credentials. User passwords are BCrypt hashes in the users table.

Q: Where are photo attachments stored?

A: As local file paths on the uploading PC. That is a known limitation on a LAN — a shared folder or BLOB storage is the next step.

Definition of done

You are done when: a client PC logs in against the server database, the fat jar runs without Maven, and your one-page connect guide is accurate enough for someone else to repeat it.

Member 2 — Startup, Login, Session & Permissions

Parts 4, 5, 6, 8 ~6 minutes

Mission: explain how the app starts, how a user proves who they are, and how the system limits what they can do.

Your 60-second opening

“The app starts in Launcher, which hands off to Main. Main loads the login screen from FXML, applies the stylesheet, and shows it. When someone logs in, AuthService looks the user up, checks the BCrypt password hash, checks that the account is active, writes an audit entry, and returns the user. That user is stored in Session. The role comes from the database — the user never picks it at login. From that role, Permissions decides what the menu shows and, more importantly, what the services will allow. So this part answers two questions: who are you, and what are you allowed to do.”

What to understand (the logic and the why)

  • Bootstrap chain. Launcher.main → Main (extends Application) → start() → ViewLoader.load("LoginView.fxml") → scene with styles.css → stage. After login, Main.setRoot swaps in the Shell, which is the permanent frame.
  • FXML + controller contract. FXML declares layout and fx:id; the controller declares matching @FXML fields and onAction handlers; initialize() runs after injection. Why: layout and behavior change independently.
  • Authentication is the only password comparison. UserDao.findByUsername → account active? → BCrypt.checkpw → touchLastLogin + audit LOGIN. Unknown user and wrong password return the same message so the app does not reveal which accounts exist; a wrong password logs LOGIN_FAILED.
  • Session is process-local. A static holder for the signed-in user for this client run; clear() on logout. Why: the desktop app needs the current user everywhere without passing it through every constructor.
  • Permissions are checked twice. The Shell hides menus, and each service re-checks with a Permissions method. Why: a hidden button is not security — the rule must live where the write happens.
  • Role codes are fixed. ADMIN, MAINT_HEAD, PERSONNEL, STAFF in Role must match roles.role_code in the database; Role.fromCode is the bridge.

Your tasks (tick when the acceptance test passes)

  • Log in as every seed account — admin, mhead, tech1, tech2, jcruz, msantos — and record the menu each role sees. Accept: a role → menu table you can show.
  • Test the failure paths: wrong password, a deactivated account, and the database stopped. Accept: friendly messages, no stack trace, no crash.
  • Prove service-side enforcement: show that hiding a menu is not the only defense — point at the Permissions call inside a service. Accept: you can explain the difference in one sentence.
  • Trace logout: Session.clear(), return to login, and confirm the next user does not inherit the previous identity. Accept: no stale name or role on screen.
  • Verify role codes in Role match roles.role_code. Accept: a SELECT proves it.

Demo script (about 3 minutes)

  1. Launch the app and point out the login branding and centered layout.
  2. Log in as admin; show the full menu and the Shell layout.
  3. Log out, log in as jcruz (staff); show the reduced menu.
  4. Open the audit log and show the LOGIN row and one LOGIN_FAILED row from your negative test.
  5. Open Permissions and the service call site; say “hidden in the UI, enforced in the service.”

Likely questions and short answers

Q: Why not let the user choose a role at login?

A: That is privilege escalation. The role is authoritative in the database and read after authentication.

Q: Why BCrypt instead of MD5 or SHA-256?

A: BCrypt is deliberately slow and salted, so stolen hashes are expensive to crack. General-purpose hashes are fast and unsafe for passwords.

Q: Is hiding a button enough security?

A: No. Services re-check permissions before any write, so the rule holds even if the UI is bypassed.

Q: Is there a “remember me” or persistent login?

A: No. The session lives in memory for that run and ends when the app closes or the user logs out.

Q: What happens if the database is down at startup?

A: Login fails with a clear connection message; the app stays open instead of crashing.

Definition of done

You are done when: you can show the role → menu table for all four roles, demonstrate two failure cases without a crash, and point to the exact service line that re-checks permission.

Member 3 — The Module Pattern & Assets (Facilities / Equipment)

Parts 7, 9, 11 (assets) ~6 minutes

Mission: own the repeatable recipe every screen follows, and prove it with Facilities and Equipment.

Your 60-second opening

“Every module in this system follows one recipe: a table, a model, a DAO that holds the SQL, a service that holds the rules, an FXML screen, and a controller that connects them. Facilities is the cleanest example, so I use it to teach the pattern. Once you understand Facilities, Equipment is the same code with different fields. That is why we could add modules quickly, and why a bug has exactly one place to hide: either the SQL, the rule, or the screen.”

What to understand (the logic and the why)

  • Five layers, one direction. FXML (layout) → Controller (events, table binding) → Service (permission, validation, uniqueness, audit) → DAO (parameterized SQL) → Database. Models and Drafts carry data between layers.
  • Why separate them. SQL changes without touching the UI; rules are testable without a screen; each rule exists in exactly one place. A controller that contains SQL becomes impossible to reuse and easy to break.
  • Read path. initialize() → refresh() → background Task<List<Facility>> → FacilityDao.search → TableView items. Why a Task: a database call on the JavaFX thread freezes the window.
  • Write path. dialog → FacilityFormController.draft() → FacilityService.create/update → requireManage + validate + existsCode + audit → FacilityDao → refresh.
  • Archive, never delete. setActive(false) keeps the row so requests, equipment, and history still resolve. Deleting a facility would orphan every record that points at it.
  • Drafts exist for a reason. Form input is validated before a database ID exists; the Draft keeps “what the user typed” separate from “what is stored.”
  • Dialogs need the stylesheet too. A new Scene does not inherit CSS, so dialogs call ViewLoader.applyAppStyles(parent).

Your tasks (tick when the acceptance test passes)

  • Draw the five-layer diagram for Facilities from memory after reading the code. Accept: you can whiteboard it without notes.
  • Add a facility, then try a duplicate code. Accept: a friendly validation message, not a raw SQL exception.
  • Edit a facility and confirm the form prefills every field. Accept: no blank fields on edit.
  • Archive and restore a facility; confirm it leaves the active list and history still resolves. Accept: you can explain the no-delete rule.
  • Repeat one operation on Equipment and name the differences (facility link, condition). Accept: same pattern, different fields.
  • Prove a staff account cannot manage assets. Accept: the service refuses, not just the menu.

Demo script (about 3 minutes)

  1. Show the Facilities list with search and condition filter.
  2. Add a facility with a duplicate code → show the error → fix it → save.
  3. Edit the new row and show the prefilled dialog.
  4. Archive it, then restore it.
  5. Run a SELECT to show the row and the audit entry.
  6. Open Equipment and point out the identical structure.

Likely questions and short answers

Q: Why a Draft class instead of using the model directly?

A: The form has no database ID yet, and validation must happen before insert. The Draft separates input from the persisted row.

Q: Why not put SQL in the controller?

A: It duplicates queries, risks injection, and cannot be reused or tested. The DAO is the only place SQL lives.

Q: Why archive instead of delete?

A: Requests, equipment, and history reference facilities. Deleting would break referential integrity and lose history.

Q: How is search protected from SQL injection?

A: Every value is a bound parameter in a prepared statement; the keyword becomes a LIKE parameter, never string concatenation.

Q: Why does the table not freeze during loading?

A: Queries run in a background Task and the UI updates on the JavaFX thread when it completes.

Definition of done

You are done when: you can teach the five-layer recipe in under two minutes, show a validation failure and a permission failure live, and explain why archive beats delete.

Member 4 — Workflow & Accounts: Requests, Users, Registration, Google, Schedules

Parts 9 (requests), 10, 11 (schedules) ~6 minutes

Mission: own the core workflow — a request from report to closure — and the account lifecycle that decides who can act.

Your 60-second opening

“The heart of the system is the request. A teacher reports a problem; the head assigns it; personnel work on it; the head closes it. Each step is a status transition with rules about who can move it and when a remark is required, and every move is recorded. The second half of my part is accounts: people can register, but they cannot log in until an admin approves them and assigns the correct role. Google sign-in follows the same rule — a verified email can match an existing active user, but a new person still becomes a pending request. Approval is never bypassed.”

What to understand (the logic and the why)

  • Three scopes, enforced twice. ALL for admin/head, MY_TASKS for personnel, MY_REQUESTS for staff. The list query is scoped, and RequestDetailService.canView re-checks before showing a detail page.
  • Statuses. PENDING → ASSIGNED → IN_PROGRESS → COMPLETED → CLOSED, plus ON_HOLD, REJECTED, CANCELLED. The active rules live in StatusFlow: allowed, canMove, requiresRemarks, isTerminal. Personnel get a restricted subset. Why: the workflow cannot be skipped, and negative decisions must be explained.
  • Remarks are mandatory for REJECTED, ON_HOLD, and CANCELLED. Why: accountability for stopping or blocking work.
  • Assignment is a head action. PENDING becomes ASSIGNED; an assigned request can be reassigned. Only Permissions.canAssignRequests passes.
  • Detail page shows info, status actions, comments, history, and attachments; “back” returns to the list and refreshes it.
  • Registration is a request, not an account. RegistrationService.submit writes to account_requests with a BCrypt hash, the requested role, and PENDING. UserService.approveRequest creates the real user with the role the admin chooses; rejectRequest closes the request.
  • Google Option A is config-gated. The button appears only when GoogleOAuthService.isConfigured(). Flow: PKCE + loopback browser → verified email → active match signs in; inactive is blocked; no match becomes a pending request. Secrets come from config or -D, never code.
  • Schedules plan recurring maintenance; markDone records completion and computes the next due date.

  2. As head, assign it to personnel.
  3. As personnel, move it to IN_PROGRESS, then COMPLETED with a remark.

Likely questions and short answers

Q: Why require admin approval for registration?

A: Otherwise anyone could self-assign a privileged role. Approval keeps role assignment under administrative control.

Q: Why are remarks required on some statuses?

A: Rejecting, holding, or cancelling work needs a recorded reason for accountability and follow-up.

Q: What stops personnel from closing a request?

A: StatusFlow gives personnel a restricted transition set, and RequestDetailService.changeStatus re-checks it.

Q: Does Google sign-in skip approval?

A: No. It only signs in an existing active user by verified email. A new email still creates a pending request.

Q: Where are request photos stored?

A: In the local uploads folder, with the path saved in the database. On a LAN that means each PC has its own files — a known limitation.

Definition of done

You are done when: you can run the full lifecycle live, show two blocked actions, and state clearly which account flows are verified and which are pending credentials.

Member 5 — Reporting, Audit, Quality & Defense

Parts 11 (reports/audit), 12 (testing), 13 ~6 minutes

Mission: prove the system is correct, visible, and explainable — then package it for the defense.

Your 60-second opening

“My part is trust. Reports turn the data into decisions: how many requests, by status, by category, with cost and downtime, over a date range. Audit gives accountability: who did what and when. Then I run the quality pass across all four roles, document what works and what is still limited, and prepare the defense package. I also own the debug method: follow Controller → Service → DAO → Database and change one thing at a time. If something looks wrong on screen, those four layers tell you where it actually broke.”

What to understand (the logic and the why)

  • Reports are period-based. ReportDao.summarize(from, to) returns a ReportSummary; the controller renders counts, breakdowns, and charts. Why a date range: “all time” hides trends and makes totals meaningless for a term.
  • Exports must match the screen. CSV and PDF are generated from the same summary the UI displays, so a mismatch is a bug, not a formatting choice. PDF uses PDFBox.
  • Audit is append-only. AuditDao.log writes; search reads; there is no edit or delete path. Why: an audit trail you can change is not evidence.
  • Dashboard is role-aware. DashboardDao.load aggregates; personnel see their own workload. applyMonthlyChart and applyDonut render the summary.
  • QA is a matrix, not a vibe. Four roles × menus, CRUD, workflow, and error paths; each cell is pass/fail with a note.
  • Debug flow. Is the row in the database? Does the DAO return it? Does the service allow it? Does the controller display it? That order isolates almost every bug.

  • Export CSV and PDF, open both, and compare rows and totals to the screen. Accept: identical content.
  • Audit review: perform five known actions, then confirm five entries with actor, time, entity, and details. Accept: you can point at each one.
  • Run the role QA matrix (4 roles × menus, CRUD, workflow, errors). Accept: a filled table with pass/fail and notes.
  • Negative tests: invalid input, duplicate code, illegal transition, database down. Accept: no crash; every case has a clear message.
  • Prepare the defense package: demo order, known-limits slide, and a 10-minute run-through. Accept: someone else can present from your notes.

Q: How do you know the report is correct?

A: I reconciled the totals against direct SQL counts for the same date range, and the CSV/PDF match the screen.

Q: Can the audit log be edited or deleted?

A: There is no UI or DAO path for it. Entries are appended and only searched.

Q: What is not finished?

A: Google sign-in needs real credentials; the LAN setup needs the school host; photos are local-only; and there is no automated test suite yet.

Q: A screen is blank. How do you debug it?

A: Check the database row, then the DAO result, then the service permission/validation, then the controller binding — in that order.

Q: What would you do with more time?

Five Rules for Every Demo

  1. Follow the script, not your memory. Rehearse the exact clicks; improvising is where demos break.
  2. Show the database behind the screen. One SELECT proves the UI is not faking it.
  3. Show one guard. Every member demonstrates a permission or validation rule that blocks something.
  4. Show one failure. A wrong password, a duplicate code, or an illegal transition — handled without a crash.
  5. Say “pending setup” when it is pending. Real credentials, the school LAN, and real data are environment items, not finished features.
Why this matters: panels rarely fail a team for a missing optional feature. They fail teams that cannot explain their own code or that overclaim what works.

Shared Checklist (All Members)

  • I can build and run: mvn -q -B package -DskipTests and mvn -q javafx:run.
  • I can explain my part’s logic and why, not just the buttons.
  • I can trace one action from my screen to the database row and back.
  • I can name the exact files I own and the methods that matter.
  • I have run my demo once, start to finish, without notes.
  • I know which of my items are pending setup and can say why.
  • I have read Part 0 so I can connect my part to the whole system.
  • I know who I hand off to and who hands off to me.
